### U1 为什么不能直接把 pending 改成 reviewed

- 静态 import 闭包不是完整调用图。例如 `FileUploader` 通过注入网关调用 DMS，不能只看到共享组件的 emit 就停止追踪。
- 同一操作可能含详情读取、候选查询、写入和成功回读；只登记保存接口会遗漏必要权限。
- 同一回调有条件分支。例如用户角色抽屉只有拥有分配能力时才查询可分配角色，不能无条件把该查询塞进撤销角色模板。
- 源码 hash 只能证明“文件是否变化”，不能证明“声明是否完整”。现有审查器以文件记录为粒度，后续需要补可追溯的调用链/候选分类证据，并确认注入 provider 等依赖变化会让相关证据失效。
- 已有 [首批通信链核对记录](iam-maintenance-communication-review.md) 可以复用，但它明确不是全通信链已验收的证明。

这是前端需要继续完成的工作，**不需要后端再提供同一份接口清单，也不能让维护 Skill 猜测缺失映射**。

## 4. 质量结果如何理解

上一轮完整 `pnpm quality` 的视觉原始结果是 **486 通过、90 失败、24 跳过**：

- 18 项 Teleport Dialog 资源指令警告已修复，修复后专项 162 项及新七页批准基线 21 项通过。
- 其余已知失败为 69 项截图差异、3 项培训概览溢出；“此前已存在”只说明它们不是本次新增标记独有的问题，不表示无需修复或可从总验收中豁免。
- 未调查完的截图差异不能一概称为“基线过期”，也不能据失败数量推断有同样数量的页面缺陷；同一页面在三个视口可能产生多项失败。

本次文档整理时再次执行全量检查，最终结果记录在下方。测试使用项目 Playwright 与模拟 API，不是对生产环境发起维护写入。

本次 210 项失败按错误证据分为：

- **66 项截图差异、2 项培训概览横向溢出**：本轮实际执行到的失败；与历史 69 / 3 分开记录，不代表另外几项已经修好。
- **140 项连接拒绝、1 项连接重置**：均指向本地 `127.0.0.1:4173` 前端测试服务。中途检查确认该端口已不再监听，而 4174 Preview 服务仍在。服务退出的根因尚未确定；由前端测试环境维护者排查生命周期和隔离后重跑，不能转交后端补接口。
- **1 项页面跳转断言超时**：1440 视口的 Permission 写入结果未知恢复用例，预期进入 `/iam/permissions/configuration?permissionId=102`，实际停留在 `/iam/permissions`。此项应在稳定服务环境独立复现，再判断是交互回归还是环境影响；不能仅凭同轮连接失败就直接归因。

因此，本轮证实“全量未通过”，但**210 不是已确认的业务缺陷数**。该轮不能用于判断全部生产交互是否正确，也不能用历史专项通过抵消；U6 必须包含稳定测试环境后的完整复跑。原始错误和 trace 位于本工程 `test-results/`，再次执行测试会覆盖，应在后续排查前留存必要证据。

## 5. 谁现在需要做什么

1. **前端开发会话（本会话）**：继续完成 U1～U3；处理或协调 U4/U5 并完成 U6。普通一致性检查通过，不得冒充完整性通过。
2. **系统资源维护会话**：复核前端产物、模型与未决项；在不完整期间不执行全量覆盖或删除。前置条件具备后，承担 U7 的计划、受控同步和授权回读。
3. **后端/部署方**：目前不需要再为 U1～U6 重复补接口。进入 U7 时提供与目标部署对应的运行清单、能力与范围；只有发现具体缺失/冲突后，才提出明确后端修复任务。
4. **用户**：无需补 PRD 或逐项手工登记资源。只有确需改变批准视觉、扩大维护范围或执行环境授权变更时，需要确认对应决定。

## 6. 允许全量同步前必须分别通过的条件

- **前端声明就绪**：正式页面和占位/辅助分类有完整证据，通信与模板验收完成，`iam:maintenance:ready` 真正通过。
- **工程质量就绪**：完整 `pnpm quality` 通过；目前截图/布局失败和声明未完成是两条独立问题线，解决其中一条不会自动解决另一条。
- **环境执行就绪**：维护会话确认目标环境、部署版本、App/Tenant/角色和操作权限，取得完整快照，审查计划及影响后再执行。

`iam:maintenance:check` 只校验当前声明及产物一致性，允许如实表达 pending；`iam:maintenance:ready` 检查声明完整性。**后者不会自动运行全量视觉测试，也不会验证线上数据库。** 三层条件不能互相替代。

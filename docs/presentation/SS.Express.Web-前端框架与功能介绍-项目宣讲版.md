## 一、项目定位

SS.Express.Web 是面向物流平台管理与运营人员的统一 Web 前端工程。它不是某一个运输子系统的独立界面，而是能够承载多个业务 App、共享登录状态、导航框架和设计体系的综合操作平台。

从业务宣讲角度，平台围绕“人、车、船、货、港、单、能”，融合运输资源与车船运营管理、多式联运任务管理、车船港智能协同调度、电子运输记录与单证管理、港口收货与装船协同、外协水运及航次管理、多式联运全程追溯与异常预警、运力补能与能源协同管理、经营数据分析与可视化调度中心九大核心模块。

在统一前端体验下，组织权限、员工培训、数据安全和运行保障作为公共基础贯穿业务过程，并呈现逐步拓展 AI 智能分析与跨系统数据协同的综合调度愿景。

### 1.1 面向哪些使用者

- **集团及租户管理人员**：管理组织、人员、角色和协作范围。
- **运输与调度人员**：关注任务、资源、执行节点和异常处置。
- **车船运营与外协管理人员**：关注运力可用性、运营状态和合作履约。
- **港口及交接协同人员**：关注到货、收货、集结、装船与交接差异。
- **培训及安全管理人员**：组织培训考试，查询人员学习与执行记录。
- **经营管理人员**：从总体态势进入业务明细，了解效率、成本与履约表现。

这些是宣讲中的业务角色视角，不是新增系统角色、租户类型或授权范围的配置要求。

### 1.2 希望解决的前端使用痛点

传统物流管理界面容易出现入口分散、系统切换频繁、业务信息割裂、表格和操作方式不一致等问题。运营人员既要反复查找任务与资源，又要记住不同页面的使用方法。

本项目通过统一框架、明确的信息层级和可复用的交互模式，为用户提供连续的工作环境：**在同一个平台中找到业务、看清状态、完成操作、追踪结果。**

## 二、当前前端项目框架

### 2.1 总体结构：统一平台，按业务分区

当前工程采用“认证前独立入口、认证后单页应用壳层、子系统分组、Feature 业务模块化”的结构。

登录后，用户进入统一框架；不同业务页面加载到框架内容区，不重复建设顶部导航、左侧菜单和账号区域。IAM、TMS、VMS 等业务区域在代码上分开组织，在体验上共享一套平台外观与基础操作方式。

| 工程区域                         | 当前职责                                                | 宣讲中的含义                               |
| -------------------------------- | ------------------------------------------------------- | ------------------------------------------ |
| `src/app`                        | 应用装配、路由、会话、布局与全局能力连接                | 平台的统一入口和运行框架                   |
| `src/features`                   | 按子系统和业务 Feature 组织页面、组件、接口、类型与状态 | 各业务能力的独立承载区                     |
| `src/shared/components`          | 通用组件与标准页面模板                                  | 一致的表格、表单、抽屉和页面骨架           |
| `src/shared/business-components` | 可跨业务复用的业务组件                                  | 减少重复建设，保持同类操作一致             |
| `src/shared/api`                 | 统一请求、地址配置、认证信息与错误处理                  | 页面连接后端的公共基础                     |
| `src/shared/styles`              | Design Token 和全局样式                                 | 颜色、字号、间距、尺寸等视觉规则的统一来源 |
| `UIDesign`                       | 独立原型预览、评审和视觉证据工作区                      | 在正式接入业务前看清页面效果与交互         |
| `standards`、`docs/page-specs`   | 标准入口、注册信息、页面规格与校验约束                  | 支撑跨页面一致性和可检查的开发过程         |

当前 `src/features` 中包含平台门户、IAM、TMS、VMS、培训和 DMS 文件接入等区域。前端 DMS 门户主要由 `platform` 相关页面承载，`features/dms/files` 则提供文件接入能力；两者不能简单等同于一个已经完整建成的数据分析系统。

### 2.2 技术基础

| 领域       | 当前采用的主要技术                                     |
| ---------- | ------------------------------------------------------ |
| 页面开发   | Vue 3、TypeScript、Vite                                |
| UI 组件    | Element Plus、项目共享组件                             |
| 路由与状态 | Vue Router、Pinia                                      |
| 接口通信   | Axios 统一客户端及 Feature API 封装                    |
| 数据展示   | ECharts、共享图表配置与主题                            |
| 视觉组织   | SCSS、CSS Variables、Design Token、本地图标资源        |
| 日期与时间 | Day.js 与项目通用处理能力                              |
| 工程检查   | ESLint、Prettier、TypeScript、静态标准检查、Playwright |
| 依赖管理   | pnpm                                                   |

本工程面向桌面管理与运营场景，统一验证 `1366×768`、`1440×900`、`1920×1080` 三种桌面视口。本文不将桌面后台直接描述为司机移动端，也不据此声称已完成全部移动设备适配。

## 三、统一工作台与页面体验

### 3.1 一套框架承载多个业务系统

统一 AppShell 为认证后的页面提供稳定的工作环境：

- **左上品牌区域**：展示 Logo、品牌名和较小字号的平台名称；前端已具备读取后端配置及缺省回退的能力，实际配置效果取决于后端返回。
- **顶部 App 导航**：按用户可访问的应用展示入口，使用服务端返回的应用名称与目录顺序。
- **左侧模块和菜单树**：随所选 App 加载相应导航，支持展开、收起和侧栏折叠。
- **面包屑与操作区**：说明当前所在位置，集中承载页面级操作，减少重复标题占用。
- **中央内容区域**：统一承载列表、详情、表单、工作区和总览页面。
- **底部账号区域**：展示头像、用户名与当前租户信息，帮助用户识别操作身份。

欢迎页与运营总览采用不同入口语义：用户进入平台后不必都拥有 Dashboard 权限；无对应总览权限时，可使用欢迎页承接基础访问。

框架中存在搜索、通知等交互入口，但当前部分行为仍为提示或建设中状态，不能将入口存在表述为全平台搜索、消息中心已经完成。

### 3.2 少量标准页面模式，覆盖不同工作场景

| 页面模式     | 常见场景                                 | 用户体验价值                         |
| ------------ | ---------------------------------------- | ------------------------------------ |
| 列表页       | 条件查询、状态筛选、结果浏览和行级操作   | 以数据为中心，便于高频处理           |
| 详情页       | 对象资料、关联信息和过程记录             | 集中理解业务对象及其上下文           |
| 表单页与抽屉 | 新建、编辑、配置和局部维护               | 在明确范围内完成修改，减少不必要跳转 |
| 分步向导     | 信息较多、分阶段确认的创建流程           | 分解填写压力，便于回看与确认         |
| 工作区       | 树状结构、主从列表、资源选择和多面板协作 | 同时观察对象与关联关系               |
| 总览页       | 指标、趋势、任务摘要和业务入口           | 从总体信息进入具体工作               |
| 独立认证页   | 登录、租户上下文选择等认证场景           | 与业务壳层分离，聚焦身份确认         |

这些模式已有共享模板基础，不意味着所有宣讲功能都已经落入具体页面。

### 3.3 一致性体现在日常操作中

项目通过 Design Token、公共组件和页面模板统一视觉与操作，而不是让每个页面单独决定颜色、尺寸和布局。

列表和查询区域强调紧凑但可读；常见的查询、重置、分页、详情、编辑、确认与错误反馈采用公共能力。长文本、树状内容和大结果集分别由适用组件处理，避免信息被裁切或操作无法触达。

普通列表随当前页数据行数自然展开，由标准内容容器承担纵向滚动；复杂工作区和抽屉则按其承载方式组织内部滚动。其目的不是让所有页面一样高，而是在不同浏览器高度下保持内容可访问、操作可完成。

## 四、九大核心模块的前端功能蓝图

> 本章描述面向用户的业务功能与操作场景，仅用于宣讲。它不规定新增页面、菜单数量、路由地址、字段、接口或开发先后顺序，也不要求九大模块分别创建九个 App。

### 4.1 运输资源与车船运营管理

**让运营人员看清“有哪些资源、处于什么状态、是否适合当前任务”。**

- 从资源总览进入车辆、船舶、人员和外协运力资料，按状态与业务条件查找资源。
- 集中查看运力能力、资质证照、维保检修及在运、待命、不可用等信息。
- 关联资源承担的任务与运营记录，帮助用户理解资源状态背后的业务原因。

该模块在整体体验上为任务分配、调度和补能提供资源视角，减少在多个台账之间反复核对的信息成本。

### 4.2 多式联运任务管理

**围绕一项运输需求，查看各运输区段与交接环节的整体进展。**

- 通过任务列表查找待安排、执行中、已完成和异常运输事项。
- 在任务详情中联看货物、起讫地、时效、责任主体和公路、水路等运输区段。
- 区分单一区段完成与整项运输完成，关联资源、执行记录和交付凭证。

任务作为跨模块的业务主线，帮助用户从“查某辆车、某个航次”回到“这一票货整体进行到了哪里”。

### 4.3 车船港智能协同调度

**在一个工作视角中衔接车辆到达、货物集结、船期与港口作业窗口。**

- 联看待调度任务、可用运力、预计到达和作业时段，减少信息分散。
- 提示资源占用、时间冲突和衔接风险，帮助调度人员比较不同安排。
- 对任务改派、时段调整和资源替换呈现影响与反馈，保留人工确认的业务责任。

“智能协同”在宣讲中包括规则辅助、信息联动和决策建议，不代表当前已经实现自动最优调度或无需人工干预的调度系统。

### 4.4 电子运输记录与单证管理

**让运输过程、交接结果与证明材料能够一起查看。**

- 按运输任务或交接环节查找运单、交接记录、装船清单、回单和相关附件。
- 将结构化业务信息与照片、文件等材料关联展示，支持有权限的预览或下载。
- 展示记录状态、关联对象及处理过程，辅助补充材料、核查差异和业务复盘。

现有统一文件接入能力为附件处理提供基础，但文件上传组件并不等于完整电子单证系统已经建成；法律意义上的电子签章、电子提单等能力不在本文中作已实现声明。

### 4.5 港口收货与装船协同

**把陆侧到货和水侧装船放在连续的业务视图中。**

- 联看预计到港、实际收货、货物集结、待装及装船确认等信息。
- 按任务、批次或航次核对货物交接情况，突出数量差异和未齐套事项。
- 帮助业务人员识别“车辆已到但交接未完成”“货物已收但尚未装船”等状态差异。

该模块的宣讲重点是跨参与方协同和交接可见，不表示替代港口已有的生产控制系统。

### 4.6 外协水运及航次管理

**让外部船运安排成为整体运输过程中的可见环节。**

- 查看外协承运商、船舶、航线、航次与承运资料。
- 将航次计划、挂靠港、装卸节点和所承接运输任务关联展示。
- 跟进预计与实际离到港、航次变更、履约异常及业务对账资料。

用户可以从任务追溯承运航次，也可以从航次了解所影响的任务；费用信息展示不等同于财务核算、支付或完整结算能力已经实现。

### 4.7 多式联运全程追溯与异常预警

**回答“发生了什么、发生在哪里、由谁跟进、是否已经解决”。**

- 按任务汇集区段执行、位置、到离场、交接、装卸与签收等事件。
- 将超时、交接缺失、货物差异和状态停滞等异常集中呈现，支持按业务范围查找。
- 从异常进入相关任务、资源、单证及处理记录，形成有上下文的跟进过程。

位置展示、更新频率和预警准确性取决于实际接入的数据。宣讲中不将示意地图或静态轨迹描述为已经接通的实时车船监控。

### 4.8 运力补能与能源协同管理

**把补能需求与运输执行、资源可用性放在一起考虑。**

- 按适用业务展示车辆或船舶的能源状态、补给需求及相关执行任务。
- 联看补能时段、服务点条件和运输衔接，辅助人工安排加油、充电、换电等作业。
- 汇集能源补给、用能及费用记录，为资源运营和经营分析提供查询视角。

车辆充换电、船舶补给等场景应区别表达；站点实时状态和预约协同依赖外部接入，不是当前已有通用组件即可保证的能力。

### 4.9 经营数据分析与可视化调度中心

**从总体态势发现问题，再进入具体业务查看原因。**

- 面向调度呈现任务进展、运力状态、关键节点、异常分布和待处理事项。
- 面向经营呈现运输量、履约时效、等待时间、资源利用、外协表现与能源成本等分析视角。
- 通过指标、趋势、地图和明细联动，把可视化展示与日常操作联系起来。

现有工程已有图表与总览页面基础，但部分总览数字和操作仍为演示内容，不能作为实时经营结果或已完成统计接口的证明。指标口径与数据可用性需由实际业务另行确认。

## 五、贯穿业务的公共能力

### 5.1 组织权限与多租户协作

当前前端已有集团、租户、组织、岗位、用户与成员、角色等管理页面，以及新版权限资源、Permission、权限包、角色授权和用户有效权限页面。

在用户体验上，这些能力分别解决组织是谁、成员属于哪些租户、以什么角色参与工作，以及可以看到哪些页面和操作等问题。用户有效权限页面用于查看权限结果；角色分配与授权维护是不同的操作场景，不混同为给用户直接随意勾选所有资源。

页面与按钮通过登记的资源标识配合后端权限结果控制访问。前端的可见性和可操作性是体验层防护，不能替代后端对接口及数据范围的校验。

### 5.2 员工培训与运营基础

当前培训区域已有课程、题库、试卷、考试配置、培训概览、计划、计划详情、任务详情、员工培训档案和专项统计等正式页面入口。

培训业务以计划组织任务，以任务关联课程、考试和参与员工，通过学习与考试状态、人员明细和统计信息帮助管理者了解执行情况。年度及常设培训等能力为不同培训组织方式提供承载。

在整体平台宣讲中，可将这些页面用于说明入职培训、岗位知识和安全流程宣贯的数字化基础。培训结果自动限制派车、装船或其他作业权限，并不能由本文直接推定为已经完成。

### 5.3 数据安全与可靠操作

前端通过统一会话、认证请求、页面权限、操作权限及错误处理机制，与后端共同维护访问边界。敏感资料、文件和跨租户数据仍以服务端授权为准。

表单校验、提交反馈、异常提示和未保存内容确认等共享交互，有助于减少误操作和不清晰的结果状态。图片及文件处理使用统一接入能力，避免不同页面重复定义不一致的上传行为。

这些是安全与可用性的组成部分，不等于浏览器能够独立保证数据安全，也不构成合规认证、数据防泄漏或完整灾备能力的承诺。

### 5.4 运行保障与体验质量

工程已配置代码检查、类型检查、构建、标准约束与浏览器测试等质量机制，并以多种桌面视口观察页面布局和交互表现。

其价值在于让共性问题尽量在共享组件和标准层修正，而不是逐页追加不一致的补丁。加载、空数据、错误和无权限等状态也需要作为完整页面体验的一部分，而不是只展示有数据时的理想界面。

存在质量门禁不代表当前全量检查一定通过；本次宣讲文档不对全站可用率、性能规模或生产运行状态作未经验证的结论。

## 六、UIDesign 机制体现的产品建设方式

UIDesign 是独立的页面预览与评审工作区，不是另一套生产系统。

项目把“页面看起来怎样、使用起来怎样”和“接入哪些真实数据、拥有什么权限”分开装配。新机制下，Preview 与正式页面复用同一套页面结构，前者使用明确的场景数据，后者连接真实接口和生产上下文。

从项目宣讲角度，可概括为三个特点：

1. **先看清再确认**：把页面结构和关键交互呈现为可操作预览，方便业务人员审阅。
2. **确认结果可追溯**：通过页面规格、人工审批与视觉证据记录已确认内容，不把草稿等同于正式成果。
3. **设计和实现尽量一致**：共享页面结构、组件和 Token，减少原型确认后重新实现导致的样式与行为偏差。

这说明项目具有受约束的设计与实现机制，而不是承诺“一键生成后无需审核”。本文不修改现有 UIDesign 工作流，也不批准任何新页面或视觉基线。

## 七、面向多式联运的一次完整使用场景

以下是用于宣讲的示意业务，不表示端到端生产链路当前已经上线。

| 用户工作阶段 | 前端帮助用户理解和处理的信息                 | 关联模块                     |
| ------------ | -------------------------------------------- | ---------------------------- |
| 接收运输需求 | 货物、路线、时效、区段与责任方               | 多式联运任务管理             |
| 准备运力     | 车船状态、人员信息、可用资源和外协能力       | 运输资源与车船运营管理       |

## 八、AI 智能分析与跨系统协同愿景

### 8.1 AI 作为辅助分析与解释入口

在数据质量、权限和评估机制具备的前提下，宣讲可展示以下潜在交互场景：

- 用自然语言查找已授权的业务资料和运营信息。
- 对任务风险、履约变化和异常原因进行辅助解读。
- 比较不同调度安排，呈现建议、约束和风险依据。
- 辅助整理运输记录与单证内容，减少重复查阅和汇总。

这些内容属于能力愿景，不表示当前已部署 AI 助手、预测模型或智能派单。涉及资源承诺、费用、安全和任务变更的关键操作，应保持明确的人工作业责任，不能用“智能化”弱化必要确认。

### 8.2 跨系统协同体现为连续的操作体验

面向客户、承运商、港口、仓储、车船定位、能源服务和财务等系统，平台的协同愿景是让用户能在统一工作环境中理解相关数据与处理结果。

前端既需要呈现业务关联，也需要区分数据来源、更新时间、可操作范围和异常状态。统一界面不意味着外部系统已经完成接入，更不意味着所有系统使用相同的业务规则或权限。

本文仅用这些场景说明综合调度潜力，不指定 AI 技术选型、外部系统清单或实施路线。

## 十、可直接用于宣讲的项目概述

> SS.Express.Web 是多式联运智慧调度平台的统一前端工作入口。它通过一套平台框架、一套设计体系和可复用的页面组件，将不同业务区域组织在连续的操作环境中。平台的功能蓝图覆盖车船资源、运输任务、协同调度、电子单证、港口作业、外协航次、全程追溯、能源协同和经营分析九大核心领域，并将组织权限、员工培训、数据安全及运行保障融入公共基础。当前工程已经形成统一框架，以及 IAM、权限治理和培训等页面基础；AI 智能分析与跨系统协同则用于呈现综合调度的拓展愿景，帮助业务从信息分散走向过程可见、协作有序和操作一致。
